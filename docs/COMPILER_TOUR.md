# The compiler, in file order

`tools/compile.rail` is the Rail compiler: one file, written in Rail, that turns a Rail
program into ARM64 assembly and links it into a signed Mach-O without leaving the process.
This document walks the file from top to bottom. Each numbered section below is one banner
in the source (a `-- ====` line, a title, a `-- ====` line), in the same order, so a reader
can open the file beside this page and never lose their place.

Every symbol named here in backticks exists: `tools/verify/tour_check.rail` (a Rail program;
`./rail_native run tools/verify/tour_check.rail`) reads this document, checks each one against the definitions in the compiler and the modules it
imports, checks that the sections below match the banners in the file in the same order,
and that each section's `Defined here` symbols are defined between that banner and the
next. CI runs it. A symbol that is renamed or removed fails the gate until this page
catches up, which is the point: a tour that drifts from its file is worse than none.

Line numbers are not given. They move with every edit; the banners and the symbols do not.

## How to read this

Read the file the way a program travels through it. A program is text; the lexer makes
tokens; the parser makes the syntax tree of `tools/ast.rail`; the checks reject what the
back end could not compile honestly; the code generator writes one assembly string per
function; the runtime is appended; `build` hands the text to the linker. Sections 1 to 13
follow that order. Section 14 is the test suite, which lives inside the compiler binary.
Sections 15 to 18 are the commands: self-compile, the dispatchers, the second back end,
and `main`.

Before editing, read [COMPILER_BOOTSTRAP.md](COMPILER_BOOTSTRAP.md): the bootstrap
cycles, the diagnostic pattern and the traps. The language itself is in
[language-reference.md](language-reference.md) and `grammar/rail.ebnf`.

## The modules the compiler imports

The first lines of the file import five modules, and two more are imported further down
where their constants used to be written (the declaration order fixes the seed).

| Import | What it is |
|---|---|
| `tools/v5/link_lib.rail` | The assembler, Mach-O linker and ad-hoc signer. `lk_link_file` takes a `.s` path and writes the signed binary. Its container is specified in [SEED_FORMAT.md](SEED_FORMAT.md) and proven by a second writer in `tools/independence/`. It imports `tools/v5/asm.rail` (the instruction encoder, with `tools/v5/arm64.rail`) and `stdlib/codesign.rail`. |
| `tools/types.rail` | Hindley-Milner inference. The code generator reads its verdicts as markers: `hm_codegen_markers` says how each parameter arrives and whether a result leaves as raw float bits. `rail types <file>` prints the types; [TYPES.md](TYPES.md) is the design. |
| `tools/ast.rail` | The syntax tree as data types: `Node`, `Decl`, `Arm`, `Guard`, `Variant`, `Field`, and the accessors (`nd_tag`, `nd_s1`, `decl_fn_name`, `ast_flat`) the rest of the file uses. |
| `tools/decimal64.rail` | A float literal's 64 bits, decided at compile time by integer arithmetic: `d64_fields` gives the sign-and-exponent field and the fraction, correctly rounded. [NUMERICS.md](NUMERICS.md) sentence by sentence. |
| `tools/decimal64_src.rail` | The same file as text (`d64_source`), generated by `tools/gen_runtime.rail`, compiled into any program that calls `parse_float` (section 13). |
| `tools/runtime_arm64.rail` | The runtime every program links, as `rt_core`, `rt_list`, `rt_io` and the other string constants, generated from `runtime/arm64/*.s` by `tools/gen_runtime.rail`. Imported in section 11. |
| `tools/runtime_arm64_data.rail` | The runtime's data section (`rt_data`), from `runtime/arm64/data.s`. Imported in section 13. |

`foreign getenv` is the one foreign declaration: the compiler reads `RAIL_ARENA_MB`.

## 1. Lexer: characters to tokens

Character classes first (`is_digit`, `is_alpha`, `is_space`, `hex_digit_val`), then the
keyword list `kw_list`, then the tokenizer. `tc` is the main loop: it walks the character
list once and builds a token list and a parallel position list, one `(tag, value)` pair per
token, with `tc2` and `tc3` handling the two- and three-character operators. The dotted
float operators (`+.`, `-.`, `*.`, `/.`, `<.`, `>.`) are their own tokens: float-ness
travels on the operator, not on the operands (section 3). `strip_nl_pp` drops the newline
tokens inside unclosed parentheses and brackets so a multi-line expression parses as one.
`tokenize` returns tokens; `tokenize_with_pos` returns tokens and positions, for error
messages with a line and a column.

The comments marked PERF are load-bearing: every empty check is `== []`, never
`length xs == 0`, because `length` walks the list and the self-compile tokenizes 551K
characters. The two forms give identical tokens, so the fixed point did not move.

Defined here: `is_digit`, `is_alpha`, `kw_list`, `tc`, `tc2`, `tc3`, `strip_nl_pp`, `tokenize`, `tokenize_with_pos`.

## 2. Parser: tokens to the typed syntax tree

A hand-written recursive-descent parser over the token list. The cursor is four one-line
functions: `cu` (current token), `ad` (advance), `sn` (skip newlines), `xp` (expect a tag).
Expressions climb a precedence ladder: `pa` parses an atom (literal, name, parenthesised
or bracketed expression, lambda via `plam`, `let` via `ple`, tuple via `ptpl`), `par`
parses application, then `pmu`, `pad`, `pcm`, `pan`, `por` and `ppi` parse
multiplication, addition, comparison, `&&`, `||` and the pipe, and `pe` is the whole
expression including `if`, `match` and `try`.

Patterns and declarations follow: `pmarms` parses match arms, `pguard` a guard,
`mk_match` turns a lowercase name used as a pattern into a binding, `ptype` and
`pvariants` parse a type declaration (`count_params` reads each constructor's fields, the
`auth` modifier included), `pdcl` parses one declaration, and `pprog_ast` parses the
program: imports first, each resolved by `resolve_bare_import`, their declarations merged
ahead of the program's own by `import_merge`, which drops a declaration imported twice along
two paths (a diamond) and keeps a genuinely different one so a real conflict still fails.

Defined here: `cu`, `ad`, `pa`, `par`, `pe`, `pmarms`, `pguard`, `mk_match`, `ptype`, `pvariants`, `count_params`, `pdcl`, `pprog_ast`, `import_merge`.

## 3. Codegen support: names, literals, float classification

The helpers every later section leans on. `cat` joins strings. `efind` and `afind` look a
name up in the local environment and the program-wide arity map (both association lists;
again `== []`, see the PERF note). `edit_dist` and `find_closest_name` are the did-you-mean
machinery behind an unknown-name error, bounded so a stdlib-heavy program does not spend
minutes suggesting. `nd_fvs` collects a lambda's free variables for closure conversion.

Then the loaders. `emit_load_int_reg` builds a 64-bit integer with movz and up to three
movk. `emit_load_tagged_reg` loads an integer literal in its tagged form (2v + 1) and
builds the chunks from v, because the product does not fit the compiler's own 63-bit int
for a literal at or past 2^61. `emit_load_float_bits` loads a float literal's bits from
the fields `d64_fields` computed: no atof anywhere, at compile time or at run time.

Then classification. `op_is_dotted` and `op_base` read the float operators. `is_int` and
`is_float` decide, from the environment's markers, whether an expression is known to be an
int or a float; `is_float_var` is the rule for a name (a local marker wins; a top-level
float constant counts only when the name is not local). `get_opc_inline` chooses the
instruction for an operator, with the guard an untyped operand needs.

Defined here: `cat`, `efind`, `afind`, `edit_dist`, `find_closest_name`, `nd_fvs`, `emit_load_int_reg`, `emit_load_tagged_reg`, `emit_load_float_bits`, `op_is_dotted`, `op_base`, `is_int`, `is_float`, `is_float_var`, `get_opc_inline`.

## 4. Expression codegen: builtins, nodes, match arms

The heart of the back end. `cg` compiles one node of the tree and returns three things:
the assembly text, the next free label number, and the highest stack slot reached. Its
arguments are the node, the environment (names to frame slots, plus markers), the arity
map, the label counter, the next slot, whether the node is in tail position, and the
frame size as text (a tail call pops the frame before it jumps). Literals come first in
`cg`; the rest is dispatched on the node tag to `cg2` (`let`, `if`, lambda, tuple
destructure, closure call) and, for an application, to the builtins.

`cg_bi`, `cg_bi2` and `cg_bi3` are one long chain of `if fname == "..."` arms, one per
builtin: `print`, `show`, `length`, `head`, `map`, `fold`, the string, array, byte and
float operations, `shell`, `spawn_thread`. A name that is no builtin is a user function and
falls out the end of `cg_bi3` as a direct bl (or a b, in tail position).

Match arms: `cg_arms` compiles the arms of a `match` as a chain of tag tests and jumps,
`cg_guard` the guard, `extract_adt_fields` the field binds, and `cg_arm_body` decides how
a float arm leaves (boxed, or raw when the function returns a float). `higher_sl` exists
because the slot a match reaches is the highest any arm reaches, not the last arm's.

Defined here: `cg_bi`, `cg_bi2`, `cg_bi3`, `cg`, `cg2`, `cg_arm_body`, `cg_arms`, `cg_guard`, `extract_adt_fields`, `higher_sl`.

## 5. Calls, closures and the float boundary

The float representation boundary, stated in the comment above `box_float_asm`: a value
the compiler has proved float is raw binary64 bits in a register; a generic location (a
tuple, list or ADT field, a closure argument, a parameter whose type is not float, a
match result) holds only tagged ints and heap pointers, so a raw float crossing into one
is boxed as a tag-6 object (`box_float_asm`) and a generic value read as a float comes
back through `unbox_float_asm`. `cg_push_args` pushes arguments as they are;
`cg_push_args_boxed` pushes them generic; `cg_call_arg` decides per argument of a direct
call from the callee's parameter markers; `norm_float_args` converts after the pops.

Closures: a closure is a heap object `[4, code, ncap, cap0, cap1, ...]`. `caps_from_env`
and `push_captured` build it, `closure_call` calls through it with `closure_arity_guard`
in front, and `pop_to_closure`, `pop_to_tuple` and `extract_tuple` move values between the
stack and the heap. `save_params` and `mk_env` lay out a function's frame: parameters at
`[x29, #16]` upward, or in registers x19 to x21 for the register variant (section 10).

Defined here: `untag_args`, `cg_push_args`, `box_float_asm`, `unbox_float_asm`, `cg_push_args_boxed`, `cg_call_arg`, `norm_float_args`, `cg_list`, `closure_call`, `closure_arity_guard`, `caps_from_env`, `push_captured`, `pop_to_closure`, `pop_to_tuple`, `extract_tuple`, `save_params`, `mk_env`.

## 6. Self-loop TCO: a self-recursive function as a register loop

A function whose parameters are all ints and which calls itself in tail position becomes a
loop with its parameters in x19 to x21. `self_loop_emit` computes the new argument values
with dependency-aware scheduling so a swap needs no spill; `check_bottom_test` recognises
the counting-down shape and emits subs plus a conditional branch at the bottom (five
instructions per iteration, the figure the README quotes); `cg_self_arg_direct` lowers an
argument expression straight into a register when it is simple enough and returns the empty
string when it is not, in which case `self_loop_emit_fallback` pushes and pops.

Defined here: `self_loop_emit`, `check_bottom_test`, `self_dec_value`, `self_loop_emit_full`, `self_loop_emit_fallback`, `cg_self_arg_direct`, `self_sub`, `self_direct_reg`.

## 7. Function analysis: parameter kinds, frame size, arities, constructor tables

What `compile_func` (section 10) asks about a function before writing a byte of it.
`all_params_int` and `body_has_float` are the syntactic questions; `mark_int_params` and
`mark_float_params` plant the `__int_` and `__float_` markers the loaders read, the second
conservatively (only a use that is unambiguously float marks a parameter; the long comment
above `param_is_float` says what is deliberately not inferred and why). `is_self_rec` and
`is_pure_fn` decide the register loop and the auto-memoisation. `max_sl` predicts the
frame size by walking the body; siblings are threaded cumulatively, and `compile_func`
re-checks against the slot the generator actually reached.

The arity map: `get_arities` builds it from the declarations, the builtin foreign
arities, and the markers `hm_codegen_markers` derives from the types; `pf_on` is the
program-wide float flag at its head. `is_bool` tells `show` when to print true or false.
`ctor_tables_asm` emits the constructor tables (how many, each one's field count and name)
that structural equality and `show` read at run time; constructor ids run across the whole
program, so one number names a constructor.

Defined here: `is_float_fn`, `body_has_float`, `all_params_int`, `is_self_rec`, `is_pure_fn`, `mark_int_params`, `param_is_float`, `mark_float_params`, `max_sl`, `get_arities`, `pf_on`, `is_bool`, `ctor_tables_asm`.

## 8. Auth types: projection, prover and verifier synthesis

For an ADT whose declaration uses the `auth` field modifier, the compiler synthesises Rail
declarations and compiles them with the program: `synth_auth_decls` writes a projection and
a digest function per type, `synth_prove_fn` and `synth_verify_fn` clone each function that
traverses an authenticated value into a prover (which appends each opened node's projection
to a proof buffer) and a verifier (which replays the traversal from a root digest and the
proof stream, and rejects on a hash mismatch), and `auth_helper_src` is the shared
length-prefix framing, as Rail source, so the encoder and decoder cannot drift. All of it
is inert for a program with no `auth` field: `inject_auth_fns` returns the declarations
unchanged, which is why `tools/compile.rail`, which declares no ADT, self-compiles
byte-identically. Synthesis is gated on `sha256_hex` being in scope.

Defined here: `collect_auth_types`, `synth_auth_decls`, `synth_ideal_prims`, `synth_prove_fn`, `synth_verify_fn`, `synth_clones`, `auth_helper_src`, `inject_auth_fns`.

## 9. Autograd: source-to-source differentiation

A function marked `#grad` gets a derivative written as a Rail syntax tree and compiled
beside it, so the gradient is itself a Rail program. `grad_deriv` is forward mode (one
directional derivative per call, through `let`, `if` and a `match` whose arms bind
nothing); `grad_rev_push` and `grad_rev_rbody` are reverse mode over a spine of flat
`let` bindings (every partial in one backward sweep, intermediates differentiated once).
The structural walkers recognise array programs by shape and emit their reverse sweep
directly: `detect_map_chain` (a chain of `float_arr_map` ending in a sum),
`detect_chain_readout` (the same with a dot-product readout), `detect_matvec_layer` and
`detect_layer_chain` (matrix-vector layers through an activation, any depth), and
`detect_residual` (a skip connection, whose fan-out sums two cotangents). Each refuses,
and falls back to forward mode, rather than emit a wrong gradient. `inject_grad_fns` is
the entry: it collects the marks, strips them, and appends what `synth_grad_decls` wrote.

Defined here: `grad_deriv`, `grad_rev_push`, `grad_rev_rbody`, `collect_grad_marks`, `strip_grad_marks`, `grad_chain`, `detect_map_chain`, `detect_chain_readout`, `detect_layer_chain`, `detect_matvec_layer`, `detect_residual`, `synth_grad_decls`, `inject_grad_fns`.

## 10. Function codegen: prologue, early return, GC slot bits, compile_func

`compile_func` writes one function: the prologue (`main` also snapshots the stack top for
the collector), the parameter save, the markers from sections 3 and 7, the frame size from
`max_sl`, the early return `mk_early_ret` plants for a function of up to three int
parameters whose body is one `if`, the body through `cg`, and the epilogue. It returns the
assembly, the function's GC descriptor, and the label counter. `compute_fn_slot_bits` is
that descriptor: two bits per frame slot (int, float, heap, or scan conservatively) so the
collector can skip what cannot be a pointer. `argf_slots` and `slots_int_params` read the
per-parameter markers once and answer the questions the rest of the prologue asks.
`compile_funcs` walks the declarations tail-recursively (`compile_funcs_loop`), consing
each function's text and joining once.

Defined here: `mk_early_ret`, `compute_fn_slot_bits`, `argf_slots`, `slots_int_params`, `compile_func`, `norm_float_params`, `compile_funcs`, `compile_funcs_loop`.

## 11. Runtime import and the optimizer

`tools/runtime_arm64.rail` is imported here, exactly where its constants were written until
2026-10-21, and `runtime_asm` concatenates them in the order every program links them. The
runtime itself is `runtime/arm64/*.s`: edit the assembly, run `tools/gen_runtime.rail`,
bootstrap twice (the generator's check mode is a CI step).

The optimizer is small and syntactic. `opt` folds constant arithmetic (`opt_op`), rewrites
`fold` over a `range` into a counting loop when the lambda has the add shape
(`opt_fold`, `is_fold_range_app`), and fuses `map` over `map` (`is_map_app`). `uses_var`
asks whether a name occurs free in a subtree and must see every node kind, because the
fold rewrite drops a binding it reports unused. `opt_decls` applies it to the program.

Defined here: `runtime_asm`, `uses_var`, `is_fold_range_app`, `is_map_app`, `opt`, `opt_op`, `opt_fold`, `opt_app`, `opt_decls`.

## 12. Checks: exhaustiveness, patterns, constructor values, type warnings, parse errors

Compile-time errors, each a count returned to `compile_checked` (section 13).
`check_exhaustiveness` walks every `match` and names the constructors no arm covers
(`build_ctor_siblings` gives each constructor its siblings); a non-exhaustive match is an
error, not a warning. `check_patterns` rejects a pattern that names no declared
constructor or the wrong number of fields. `ctor_values` rewrites a constructor used as a
value (`map Some xs`) into a lambda. `tc_infer` and `tc_check_decls` are the older forward
checker, which prints warnings (head of a non-list, arithmetic on a non-number, a wrong
arity, a call of a non-function); the types that decide representation are
`tools/types.rail`. `ce_decls` collects the parser's error nodes and `report_errors`
prints them as `file:line:col: error: message`.

Defined here: `build_ctor_siblings`, `check_match_exhaustive`, `check_exhaustiveness`, `check_patterns`, `ctor_values`, `tc_infer`, `tc_check_decls`, `ce_node`, `ce_decls`, `report_errors`.

## 13. Program drivers: compile_checked and build

Two entry points, one pipeline. `compile_program_with_file` (the file driver, with
positions for error messages) and `compile_program` (the test runner and the self-compile)
both tokenize, parse, run `inject_grad_fns`, report parse errors, run `inject_auth_fns`,
and hand the declarations to `compile_checked`, so a check added to one cannot be missing
from the other. `compile_checked` runs `inject_parse_float` (the text of
`tools/decimal64.rail` is added, as an import would be, to a program that names
`parse_float`), then `ctor_values`, `opt_decls`, `get_arities`, the three error checks
and `check_arities` (a direct call must pass exactly the declared count; Rail has no
currying), then `tc_check_decls`, then `compile_funcs`, and concatenates the header, the
functions, `runtime_asm`, `rt_data`, the constructor tables and the GC descriptor table
into one assembly string.

`build` is the one link path: the assembly goes to a mktemp path and `lk_link_file`
assembles, lays out, binds, signs and writes the Mach-O at the requested prefix. On a Linux
host it goes through `build_native_linux` instead. `trim` and `strip_trailing_ws` tidy
shell results.

Defined here: `compile_program_with_file`, `inject_parse_float`, `decls_use_name`, `compile_checked`, `arity_fn_names`, `check_arities`, `compile_program`, `build`, `build_native_linux`, `trim`, `strip_trailing_ws`.

## 14. Test harness: the suite

The suite lives in the binary: `./rail_native test` runs `run_tests`, one `run_test` call
per case, each a Rail program as a string, compiled through `compile_program` and `build`,
run, and judged by `judge_test`: a program that prints nothing asserts on its exit status,
a program that prints asserts on its whole stdout and must not have died by signal.
`run_env` runs a case under an environment variable (the arena, the collector's stress
knob). The functions named driver_ test the compiler as a command: that `run` hands back the
program's exit code, that a bare `self` refuses, that `rail types` infers, that an import
diamond builds once. `run_infer_test` checks the kind the types give a result.
`runner_judges_evidence` tests the judge itself.

`run_tests` ends by counting its booleans and printing `N/N tests passed`; the exit
status is 0 only when the count equals the literal in that line, so the runner cannot pass
with a case missing. `tools/verify/tour_check.rail` compares that literal with every count
`tests/README.md`, `CONTRIBUTING.md` and this file quote. `run_tests_quick` is a fifteen-case
smoke run. Also here, between the infer tests and the dump: `compile_file`, the plain
`./rail_native file.rail` driver, and `infer_dump_files` behind `rail infer`.

Defined here: `driver_run_returns_exit_code`, `driver_self_refuses_small_arena`, `driver_import_diamond`, `run_test`, `judge_test`, `get_test_result`, `run_env`, `runner_judges_evidence`, `run_infer_test`, `compile_file`, `infer_dump_files`, `run_tests_quick`, `run_tests`.

## 15. Self-compile

`self_compile` reads `tools/compile.rail`, compiles it through `compile_program`, and links
it through `build` to `/tmp/rail_self`. It refuses, with exit 2, below `rail_self_min_mb`
(2000 MB): under that the compiler's own source no longer fits the arena's bump window and
a self-compile that takes seconds runs for hours. The seed does not depend on the arena;
what the arena changes is time and peak memory. The fixed point is the proof:
`cmp rail_native /tmp/rail_self` is silent, and CI rebuilds the committed seed at 3000 MB
on a machine this house does not own.

Defined here: `rail_self_min_mb`, `rail_link_arena_mb`, `self_compile`.

## 16. Command dispatch: run, parse-check, linux, generate, packages

The commands `main` hands off to. `compile_and_run` compiles a file and runs it, carrying
the program's exit status home on a sentinel line (`shell` returns stdout only).
`dispatch_parse_check` parses without compiling. `build_linux` rewrites the macOS assembly
into GNU syntax for an ELF cross-link (the Linux ARM64 target; `compile_linux` is the
command). `generate_code` asks a local model for a program and compiles what comes back.
`dispatch_get`, `dispatch_pkg` and `dispatch_packages` are the package manager over
a project's rail.toml. `guards_unsupported` refuses a program with match guards for the x86 back end,
which compiles an arm without its guard.

Defined here: `join_args`, `shell_quote_arg`, `compile_and_run`, `run_report`, `dispatch_parse_check`, `build_linux`, `generate_code`, `compile_linux`, `guards_unsupported`, `dispatch_get`, `dispatch_pkg`, `dispatch_packages`.

## 17. x86_64 backend: Linux, System V AMD64 ABI, glibc-linked

A second code generator with the shape of sections 4 and 10, every name prefixed x86_: `x86_cg`,
`x86_cg2`, `x86_cg_bi` to `x86_cg_bi3`, `x86_cg_arms`, `x86_compile_func`,
`x86_compile_funcs`. It shares the front end (the lexer, the parser, the checks) through
`x86_compile_checked_x86` and emits GNU-syntax assembly for a glibc-linked Linux x86_64
binary; `compile_x86` is the command. It carries fewer features than the ARM64 back end
(no match guards, no float boundary of its own); NUMERICS.md claims nothing for it.

Defined here: `x86_cg`, `x86_cg2`, `x86_cg_bi`, `x86_cg_arms`, `x86_compile_func`, `x86_compile_funcs`, `x86_compile_checked_x86`, `compile_x86`.

## 18. Main: the command line

`parse_out_prefix` strips an optional `--out-prefix <path>` (concurrent runs on one host
must not share `/tmp/rail_out`). `main` dispatches on the first word: `test`, `quick`,
`self`, `run`, `x86`, `linux`, `parse-check`, `get`, `pkg`, `packages`, `asm`, `types`,
`infer`, `generate`, `deploy`, or a file name to compile. With no arguments it runs the
suite and then the self-compile. `dispatch_asm` writes the assembly without assembling it;
`dispatch_deploy` cross-compiles for Linux and copies the binary over ssh.

Defined here: `parse_out_prefix`, `main`, `dispatch_asm`, `dispatch_deploy`.

## What this file does not contain

The instruction encoder and the linker (`tools/v5/`), the type inference
(`tools/types.rail`), the runtime (`runtime/arm64/`), the standard library (`stdlib/`),
and the entropy beacon (its own repository, rail-plasma). The compiler is the part that
decides what instructions a Rail program becomes; everything else is what those
instructions call.
